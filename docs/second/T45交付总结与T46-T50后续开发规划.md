## 2. T45 具体做了什么

### 2.1 阶段目标

T44 的 CLI 能够执行全空间巡检，但当它进入多实例或定时调度环境后，还存在以下运维缺口：

- 运行结果只存在于进程输出中，无法稳定查询最近一次是否成功；
- 单机文件锁不能完全解决多节点同时执行问题；
- 任务超时或进程异常退出后，可能长期残留为“正在运行”；
- 平台管理员无法判断任务是否逾期、失败或发现了异常；
- 缺少可直接复用的生产调度配置。

T45 的目标是让巡检任务成为一个有记录、有状态、有超时、有告警、可检查的生产作业。

### 2.2 已落地能力

#### 2.2.1 批次运行事实表

新增 `enterprise_delivery_integrity_runs`，记录每次全空间巡检的：

- 触发人和来源（API/CLI）；
- `running/completed/failed/timed_out` 状态；
- `healthy/warning/critical` 健康度；
- 超时阈值、开始时间、完成时间和执行耗时；
- 计划扫描、已完成和异常工作区数量；
- 交付件数量、完整性异常数量和新增异常数量；
- 失败原因。

对应迁移为：

`servers/fastapi/alembic/versions/p2i6k0m4h8j1_delivery_integrity_operations.py`

#### 2.2.2 多节点并发控制

保留 CLI 非阻塞文件锁，用于同一节点的快速防重；同时在数据库运行表中增加唯一调度锁，解决多个应用节点或多个 CronJob 同时抢占任务的问题。

并发触发时：

- API 返回 `409`；
- CLI 输出 `status=skipped`、`reason=already_running`，并以成功退出码结束；
- 不会产生第二个有效扫描批次。

#### 2.2.3 超时与遗留任务恢复

通过 `ENTERPRISE_DELIVERY_INTEGRITY_TIMEOUT_SECONDS` 配置单批最长执行时间，默认 1800 秒。

- 正常超时的任务收口为 `timed_out`；
- 异常退出后遗留的 `running` 批次，会由下一次调度识别并自动收口；
- 数据库锁会被释放，后续批次可以继续执行；
- 超时原因、耗时、审计事件和管理员通知均会保留。

#### 2.2.4 运行历史 API

新增平台管理员接口：

`GET /api/v1/enterprise/admin/delivery-integrity-runs`

用于查询最近批次、执行进度、统计、健康度和失败详情。普通工作区成员无权访问平台级运行历史。

#### 2.2.5 健康检查 API

新增平台管理员接口：

`GET /api/v1/enterprise/admin/delivery-integrity-health`

健康检查能够区分：

- `never_run`：从未成功调度；
- `run_in_progress`：当前正在执行；
- `run_timed_out`：执行超过任务时限；
- `last_run_failed`：最近批次失败；
- `schedule_overdue`：超过计划周期未完成新批次；
- `integrity_anomalies`：最近批次发现交付完整性异常；
- `ok`：任务按期完成且未发现异常。

默认要求 26 小时内完成一次，可通过 `ENTERPRISE_DELIVERY_INTEGRITY_MAX_AGE_HOURS` 调整。

#### 2.2.6 平台级通知和审计

以下情况会通知启用的平台管理员：

- 批次执行失败；
- 批次执行超时；
- 下一次调度发现遗留的超时批次；
- 全空间巡检发现新增完整性异常。

通知类型为 `delivery.integrity_run_alert`。批次成功与失败同时写入审计事件，便于后续 Webhook、企业微信或外部监控消费。

#### 2.2.7 生产调度模板

新增：

`deploy/kubernetes/delivery-integrity-cronjob.yaml`

模板默认：

- 每天 02:15 执行；
- 使用 `Forbid` 禁止 CronJob 并发；
- 设置启动截止时间和作业主动截止时间；
- 保留最近成功/失败 Job；
- 复用主应用数据库、对象存储配置和 `/app_data` 持久卷。

### 2.3 T45 验收结果

- API 权限、批次记录、历史查询、健康检查和并发拦截测试通过；
- Alembic 从历史基线升级到新 head 的迁移测试通过；
- 企业平台、对象存储、知识检索、质量门禁等相关回归共 42 项通过；

### 2.4 T45 尚未覆盖的内容

T45 提供了运维后端和部署模板，但以下内容明确留给后续阶段：

- 管理后台暂未提供巡检可视化页面；
- 管理员发现异常后仍需人工进入对应工作区处理；
- 暂未自动暂停异常交付件的新增授权；
- 暂未输出 Prometheus/OpenTelemetry 指标；
- 暂未接入邮件、Webhook、企业微信或钉钉；
- 当前是平台统一巡检周期，尚未支持不同工作区的风险分级策略；
- 尚未完成生产容量、故障恢复和正式上线演练。

## 4. T46：管理员巡检运维台

### 4.1 目标

让平台管理员无需查看数据库、容器日志或直接调用接口，即可判断交付巡检是否健康并执行日常操作。

### 4.2 具体开发内容

1. 在平台管理后台新增“交付巡检”页签；
2. 展示总体健康度、最后完成时间、下次预计执行时间和是否逾期；
3. 展示最近批次列表，包括来源、状态、耗时、工作区进度、异常件和新增异常；
4. 支持手动发起全空间巡检，并正确处理已在运行的 `409` 状态；
5. 展示正在执行批次的进度并定时刷新；
6. 支持按状态、健康度、时间范围筛选批次；
7. 从异常批次下钻到具体工作区及交付中心异常列表；
8. 展示失败原因和建议操作，不向前端暴露敏感堆栈或存储路径；
9. 补齐前端 API 类型、加载态、空状态、错误态和权限态。

### 4.3 验收标准

- 平台管理员可完成“查看健康—手动巡检—查看进度—定位异常空间”的完整流程；
- 普通用户无法访问页面或平台级 API；
- 页面刷新不会重复创建任务；
- 批次执行中、成功、失败、超时、逾期均有明确状态；
- Next.js 类型检查和生产构建通过。

## 5. T47：异常处置闭环

### 5.1 目标

把“检测到异常”升级为“异常被安全隔离、分派、修复、复检并关闭”。

### 5.2 具体开发内容

1. 新增交付完整性事件/处置单模型，记录异常首次发现、最近发现和当前状态；
2. 将异常分为文件缺失、文件哈希不符、快照清单不符、引用证据不符等类型；
3. 对高风险异常交付件自动暂停新增下载授权；
4. 可配置是否同时撤销尚未消费的有效授权；
5. 支持指派负责人、填写处置说明和上传修复依据；
6. 支持重新导出、重新登记、接受风险、误报关闭等动作；
7. 修复后执行单件或工作区复检，通过后恢复授权能力；
8. 所有处置动作写入不可抵赖审计链；
9. 工作区管理员和平台管理员按权限查看、处置和关闭事件。

### 5.3 验收标准

- 新增高风险异常能够自动进入隔离状态；
- 被隔离交付件不能签发新授权；
- 未授权角色不能恢复或关闭异常；
- 复检通过后状态和授权能力正确恢复；
- 同一异常连续巡检不会生成重复处置单。

## 6. T48：企业监控与外部告警

### 6.1 目标

让巡检任务进入企业统一可观测与告警体系，而不是只依靠站内通知。

### 6.2 具体开发内容

1. 输出批次总数、成功率、失败率、超时数、执行耗时等指标；
2. 输出扫描工作区数、交付件数、异常件数和新增异常数；
3. 输出调度最后成功时间与逾期状态；
4. 增加结构化日志字段：`run_id/source/status/workspace_id/artifact_id`；
5. 提供带签名、重试和幂等键的告警 Webhook；
6. 预留企业微信、钉钉、邮件通知适配器；
7. 对连续失败、持续异常和恢复事件进行聚合与去重；
8. 给出 Prometheus 告警规则和 Grafana 面板参考配置；
9. 明确日志与指标中禁止出现 PPT 正文、下载令牌和对象存储密钥。

### 6.3 验收标准

- 外部系统可根据稳定指标判断任务失败、超时和逾期；
- Webhook 重试不会造成重复工单；
- 异常恢复时能发送恢复事件；
- 指标和日志不泄露企业内容或凭据。

## 7. T49：风险分级与巡检策略治理

### 7.1 目标

根据工作区敏感等级、交付活跃度和企业治理要求配置不同巡检策略，兼顾安全和成本。

### 7.2 具体开发内容

1. 在工作区治理策略中增加巡检开关、周期、超时和异常处置方式；
2. 支持按 L1—L4 敏感等级设置默认策略；
3. 高频交付或高敏感空间支持更短巡检周期；
4. 长期无交付空间自动降低巡检频率，但不关闭必要检查；
5. 支持全量巡检、增量巡检和指定工作区巡检；
6. 增加任务分片、并发上限和对象存储限流；
7. 记录策略版本和每个批次实际采用的策略快照；
8. 提供策略变更审计和回滚能力；
9. 保证通用 PPT 与竞标 PPT 使用统一治理框架，仅在场景规则上差异化。

### 7.3 验收标准

- 不同敏感等级按照策略执行对应巡检周期；
- 策略变更不会影响已开始批次；
- 大工作区不会阻塞全部空间；
- 可从批次记录还原当时采用的策略；
- 通用工作台不依赖竞标场景即可独立完成治理。

## 8. T50：生产验收与发布加固

### 8.1 目标

完成从“功能可用”到“满足企业生产发布条件”的最后收口。

### 8.2 具体开发内容

1. 建立不同工作区数、交付件数和文件大小下的容量基线；
2. 验证对象存储抖动、数据库重启、任务进程退出等故障场景；
3. 验证多副本同时调度时只有一个批次获得数据库锁；
4. 完成超时恢复、失败重试、告警恢复和人工补跑演练；
5. 完成数据库备份恢复与对象存储一致性恢复演练；
6. 检查 API 权限、令牌、日志脱敏、通知内容和审计完整性；
7. 明确巡检 SLO、告警响应时限和异常处置责任人；
8. 输出部署、升级、回滚、故障处理和日常巡检手册；
9. 在试点工作区完成通用 PPT 与竞标 PPT 两条真实交付链验收；
10. 固化正式发布检查表并完成发布评审。

### 8.3 验收标准

- 目标数据规模下批次在约定窗口内完成；
- 故障后不会产生重复任务、永久锁或无记录失败；
- 数据库与对象存储恢复后能重新验证证据链；
- 通用 PPT 和竞标 PPT 均通过真实业务验收；
- 运维、安全和业务负责人共同确认生产准入。

## 9. 推荐执行顺序

后续按 T46 → T47 → T48 → T49 → T50 推进。

优先完成 T46，是因为 T45 已经提供稳定的运行状态 API，前端建设不再需要临时数据结构；随后完成 T47，才能让异常真正进入业务处置闭环。T48 和 T49 分别解决企业运维接入与规模化策略问题，最后由 T50 统一完成生产验收。

若试点上线时间优先，可将 T48 的基础指标与 Webhook 提前到 T47 同期，但不能跳过 T47 的授权隔离能力，也不能在没有 T50 故障演练的情况下直接视为正式生产完成。
